\section{Dataset Details}
\label{appx:dataset-details}

\paragraph{Document roles.}
Every document in a record carries a \texttt{role} tag that determines how the ledger ground-truth generator handled it.
\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=1pt]
\item \texttt{posting\_doc}: directly generates one or more journal entries (e.g., invoices, bills, payment notices, journal vouchers).
\item \texttt{support\_doc}: provides inputs for postings derived from other documents (rate cards, contracts, schedules, tax certificates) and may appear in an entry's supporting-document references (\texttt{doc\_refs}).
\item \texttt{adjustment\_doc}: supplies period-end corrections such as depreciation schedules, rollforwards, and reclassification memos.
\item \texttt{distractor\_doc}: is intentionally neutralised and produces no entry.
\item \texttt{opening\_trial\_balance}: supplies starting balances and produces no expected entries.
\end{itemize}

\paragraph{Industries.}
Professional services, field services, retail, wholesale distribution, healthcare clinic, property management, manufacturing, and subscription SaaS.

\paragraph{Concept flags.}
Each record is annotated for the presence of several accounting concepts. These include ASC~606 revenue recognition for customer contracts with standalone selling price (SSP) allocation and fixed-asset disposals with net book value (NBV) and gain-or-loss computation. Other flags cover deferred tax from book/tax depreciation differences, lease accounting with right-of-use (ROU) asset and liability schedules, foreign-exchange invoice and settlement scenarios, and multi-jurisdictional sales tax with exemption certificates. Additional flags identify tax exemptions, multi-invoice payments, interbank transfers, reclassifications, and period-end rollforwards.

\paragraph{Inconsistency codes.}
The released forced-inconsistency taxonomy contains 23 machine-readable codes grouped into five categories. Banking and transfer codes cover closing balances, statement balances, and transfers. Invoicing and payment codes cover invoice totals, payment allocation, and duplicate references. Tax and jurisdiction codes cover rates, totals, input tax, exemption conflicts, and jurisdictional treatment. Asset, inventory, lease, and deferred-tax codes cover disposals, rollforwards, remeasurement, schedules, and deferred-tax conflicts. Contract and revenue-support codes cover SSP allocation, performance-obligation release, reclassification support, schedule rollforwards, and FX settlement or exchange-rate conflicts.

\tabref{tab:inconsistency-code-diagnostics} summarizes the 23 forced-inconsistency codes on the six-model baseline panel. The core split contains ten generated records per code, so each row aggregates 60 model attempts. Models usually recognize that a contradiction exists (1110/1380 attempts), while exact code selection is harder (994/1380). Banking, lease, and simple transfer contradictions are easiest. Input-tax, jurisdictional-tax, and performance-obligation-release contradictions remain hardest.

\paragraph{Difficulty rubric and validation.}
\label{appx:difficulty-validation}
\begin{itemize}[leftmargin=*,topsep=2pt,itemsep=1pt]
\item \textbf{L1:} single-thread postings, no tax beyond basic, no FX, and no advanced concepts, with approximately 8--12 documents.
\item \textbf{L2:} cross-document dependencies (e.g., invoice $\to$ payment receipt), straightforward tax.
\item \textbf{L3:} multi-jurisdictional tax with exemptions, FX scenarios, or simple rollforwards, with approximately 15--20 documents.
\item \textbf{L4:} ASC~606 bundled contracts, fixed-asset disposals, deferred tax, or lease accounting, with approximately 20--30 documents and longer temporal lookback.
\item \textbf{L5:} multiple concurrent advanced concepts (e.g., ASC~606 + FX + deferred tax) and/or lease modifications, with approximately 25--35 documents.
\end{itemize}

The levels are cumulative by construction: each level retains the sources of complexity below it and adds document volume, dependencies, jurisdictions, temporal lookback, or advanced concepts. The certified-accountant review judged $139/143$ compact-split assignments calibrated as written (three ``too easy,'' one ``too hard''). The independently double-reviewed overlap showed $96\%$ agreement on difficulty calibration. These judgments support practitioner-perceived ordering for the sampled benchmark records and cover the benchmark's authored complexity factors.

\paragraph{Metric definitions.}
\bsexact{} requires the model's reported \texttt{assets}, \texttt{liabilities}, and \texttt{equity} account maps and their totals to match ground truth at 0.01 tolerance. \bsrecon{} runs the model's entries through our ledger, computes the implied balance sheet, and applies the same equality check. It is an outcome-level metric and can succeed without an exact match to the expected posting set. These balance-sheet and entry metrics are reported over standard records only. On forced-inconsistency records, the expected behavior is \texttt{has\_inconsistency=True}, the correct code, empty entries, and an empty balance sheet. We therefore score them with \incCode{} and the empty-answer requirement instead of \bsexact{} or entry match.

\paragraph{Entry matching.}
Journal entries are scored at the posting level. A strict posting match requires the same debit account, credit account, amount rounded to cents, and sorted supporting-document references (\texttt{doc\_refs}). The lenient entry match uses the same account-and-amount criteria but ignores the reference set. We greedily match predictions in four passes: exact match, correct debit/credit/amount with an incorrect reference set, correct debit/credit/reference set with an incorrect amount, and correct reference set/amount with an incorrect account. Unmatched expected postings are missing. Unmatched predicted postings are extra. Duplicate identical postings are matched first-in-first-out. The allowed account list is closed, so the evaluator uses no account synonyms. Posting dates are parsed and retained for diagnostics but are outside the headline entry-match criterion. Split transactions receive credit only when the predicted posting decomposition matches the generator's expected postings.

\paragraph{Parse rate.}
Across the six completed headline baselines at $n{=}710$, parse-success rates are at least $97\%$ and five models parse at $\geq 99.8\%$. A DeepSeek Reasoner run on the same split produced outputs with a low parse-success rate under the available provider conditions, so DeepSeek Chat serves as the DeepSeek-family baseline.

\paragraph{Two-pass ledger-feedback diagnostic.}
For Gemini~3 Flash, the 2-pass ledger-feedback variant changes \bsexact{} by $+35.8$\,pp (CI $[+26.9, +44.9]$) compared with $+32.5$\,pp at 1-pass, and degrades \incCode{} by $-21.7$\,pp (CI $[-40.0, -5.3]$) compared with $-13.0$\,pp at 1-pass. The main text reports the simpler 1-pass diagnostic.

\subsection{Structural audit and validation scope}
\label{appx:structural-audit}

An independent JSON-level audit uses a replay procedure implemented separately from the generator's ledger. It checks nine invariants: unique visible IDs, dates within the record period, resolvable citations, account-taxonomy membership, positive non-self postings, section sums, the balance identity, replay of expected entries or the forced-inconsistency empty-answer convention, and label conventions. The released $710$ records and new samples of $1{,}200$ and $4{,}800$ records all pass every invariant ($6{,}710/6{,}710$). Cell-level results and audit code are released.

This audit verifies structural consistency across sampled values and combinations. Human review evaluates semantic realism, contradiction-code fit, and accounting interpretation. The $143$-record accountant review covers every industry--period--difficulty cell and every code, while the separate $75$-record set spans all industries and levels.

\section{Human Verification Protocol}
\label{appx:human-protocol}

\paragraph{Reviewer recruitment.}
The release subset was reviewed by two practising finance professionals working at major U.S.\ investment banks. Both reviewers had prior accounting and reconciliation responsibilities in their day-to-day work and received a one-paragraph briefing that scoped the task to accounting plausibility and reconciliation evidence while excluding OCR fidelity. Deterministic generator checks covered arithmetic invariants. A third reviewer, a certified accountant, independently reviewed the full compact coverage split under the same instrument and briefing. This reviewer worked separately and did not see the other reviewers' responses. All three reviewers participated as unpaid volunteers and consented to the anonymized use and public release of their review responses. No formal institutional ethics review was sought for this activity.

\paragraph{Instrument.}
Each of 75 release records was rendered as a self-contained Markdown file with seven sections: (1) record context (industry, period, currency, tax regime, difficulty, inconsistency flag), (2) the allowed-account-name list, (3) opening trial balance, (4) every document with its OCR text and role tag, (5) ground-truth journal entries, (6) ground-truth balance sheet, and (7) the verification form. The form contains six checks: document analogy, entry correctness, entry completeness, document-reference support, difficulty calibration, and overall verdict. Each check offers three options (positive, mixed, negative) plus a free-text notes field.

\paragraph{Protocol.}
The release subset contains 75 expert-reviewed records: 60 standard records and 15 forced-inconsistency records. The intended assignment used in the paper is Reviewer~1 on records 1--50 and Reviewer~2 on records 1--25 plus 51--75. This gives every record one expert review and creates a 25-record independent overlap on records 1--25. Reviewers worked independently and did not see each other's responses. The third reviewer (certified accountant) instead covered the entire compact coverage split of 143 records (120 standard + 23 forced-inconsistency). This split contains one record per industry--period--difficulty cell plus one per inconsistency code, so the review covers every such cell and code.

\paragraph{Results.}

We report these descriptive rates because the sample is small and marginals are highly skewed toward positive judgments, making Cohen's $\kappa$ less informative. \section{Reproducibility}
\label{appx:reproducibility}

\paragraph{Prompt availability.}
All evaluations use ordinary text prompts without structured-output mode or a response-schema constraint. The exact baseline prompt, record-dependent suffix, output examples, forced-inconsistency example, and citation-pressure condition are released in \path{finbalance/benchmark/prompt.py} at \url{https://github.com/Devansh1105/finbalance}. The model-visible prompt excludes document role tags.

\paragraph{Seeds.}
Dataset generation uses seed 42. Headline LLM evaluations use temperature 0.0 with no explicit seed because closed APIs expose no deterministic seed control. The best-of-3 condition uses temperature 0.7 with three independent samples.

The main evaluation split, stored under \texttt{data/main/}, uses four standard records per (industry, period type, difficulty level) cell and ten forced-inconsistency records per code, drawn from a stratified deterministic sampler. \paragraph{API reproducibility.}
OpenRouter runs and DeepSeek Platform runs use chat-completions endpoints with ordinary text prompts and no structured JSON mode or response-schema constraint. The prompt and parser alone enforce strict JSON. Each run directory stores \texttt{evaluation.json}, \texttt{summary.json}, \texttt{per\_record\_results.jsonl}, and slice tables. The evaluation files include run start/end timestamps, requested model identifier, returned model identifier, selected provider where available, service tier where available, raw response text, raw response metadata where provider terms permit, token counts, cost where available, latency, parse status, tool-use and ledger-feedback metadata, and per-record metrics. Released prompt templates and record JSON reconstruct every prompt, and released raw model outputs permit offline recomputation of the reported scores. Transient gateway errors use at most three client retries with exponential backoff for 429/5xx responses. Parse failures remain failures and are logged. Commercial APIs may later change model snapshots or routing. Requested and returned model identifiers, provider metadata, and decoding settings identify what was measured. Repeated-run ranges are reported in \appref{appx:response-controls}.

\paragraph{Bootstrap.}
All confidence intervals are paired bootstrap with $n{=}5000$ resamples drawn over a shared record-id set, so baseline and treatment are compared on matched records. CIs are reported as percentile $95\%$. These intervals cover record-level sampling uncertainty for each saved run and exclude API nondeterminism, routing changes, model updates, and future-run variance.
